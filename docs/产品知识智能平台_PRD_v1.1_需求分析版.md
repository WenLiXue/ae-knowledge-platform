# 产品知识智能平台 PRD（需求分析版）

版本：V1.1 Draft  
阶段：需求分析  
适用范围：单一产品、部门内部试点  
文档目的：明确业务目标、业务边界、用户需求和验收依据，为概要设计提供输入。

## 1. 产品定位

建设一个面向产品团队的知识与问题诊断平台，帮助团队：

1. 统一沉淀和维护产品相关知识。
2. 快速查询产品资料和历史经验。
3. 对 CDT 日志和问题描述进行辅助诊断，形成可追溯的问题分析报告。

本产品不是单纯的 RAG 系统。RAG、向量检索、关键词检索、重排序和大模型属于后续设计阶段考虑的实现方式，不构成一级业务功能。

## 2. 背景与业务问题

当前产品知识分散在飞书 Wiki、本地文件、历史 Bug、测试记录和个人经验中，主要问题包括：

- 资料分散，工作人员难以快速找到可信内容。
- 文档分类和维护方式不统一，知识质量难以保证。
- 历史问题、修复记录和验证经验无法高效复用。
- CDT 日志分析依赖少数熟悉产品的专家。
- 问题分析过程缺少统一结构，结论和证据不易追溯。

## 3. 产品目标

### 3.1 总体目标

让产品知识可管理、可查询、可复用，让产品问题能够基于日志、问题描述和历史资料得到结构化的辅助分析。

### 3.2 V1 目标

- 建立产品知识的统一入口和管理流程。
- 支持用户查询产品知识并查看来源。
- 支持用户提交 CDT 日志和问题描述。
- 输出包含现象、关键证据、可能原因和排查建议的诊断报告。
- 保留文档、任务、报告和处理状态，支持后续追溯。

### 3.3 V1 不包含

- 自动修改产品配置或生产环境。
- 自动执行修复命令。
- 替代开发、测试或技术支持人员做最终判断。
- 一开始支持所有产品和所有日志格式。
- 一开始建设复杂的跨组织权限体系。

## 4. 用户角色

| 角色 | 主要任务 |
|---|---|
| SEG 技术支持 | 查询产品资料，分析客户问题和 CDT 日志，形成初步定位意见 |
| 开发人员 | 查询设计资料、历史缺陷、修复记录，协助确认问题原因 |
| 测试人员 | 查询测试方案、测试结果和历史问题，设计验证步骤 |
| 项目经理 | 查询版本、功能、交付风险和问题处理进展 |
| 售前/售后 | 查询产品功能、部署和解决方案资料 |
| PM/PMM | 查询产品功能、规格、白皮书和对外资料 |
| 知识库维护人员 | 管理知识来源、处理入库问题、维护知识质量 |

V1 的重点使用角色建议为 SEG 技术支持、开发和测试；其他角色优先使用知识查询功能。

## 5. 业务模块划分

系统按用户可感知的业务模块划分为三部分：

```text
产品知识智能平台
├── 知识库
├── 产品知识查询
└── 问题诊断
    └── CDT 日志分析
```

### 5.1 知识库

知识库是产品知识的管理模块，负责知识的进入、维护、状态管理和查询基础。

主要内容包括：

- 飞书 Wiki 文档。
- Word、PDF、Excel 等人工上传文件。
- 产品功能、规格、部署、开发设计和测试资料。
- Bug、修复记录、支持案例和历史问题分析报告。

### 5.2 产品知识查询

产品知识查询是面向用户的查询模块，负责根据用户问题返回相关知识和答案。

输出必须包含可追溯的来源信息；当资料不足时，应明确提示信息不足，不应伪造确定结论。

### 5.3 问题诊断

问题诊断是面向实际产品问题处理的业务模块，目标是帮助用户分析当前问题并形成诊断结果。

V1 首先支持其中的 CDT 日志分析业务。后续可扩展其他输入方式和诊断场景。

## 6. 核心业务用例

### UC-01：知识入库

目标：将飞书 Wiki 或本地文件纳入知识库。

主要参与者：知识库维护人员、文档上传者、系统任务。

输入：文档链接或本地 Word/PDF/Excel 文件。

主流程：

1. 用户选择 Wiki 文档或上传文件。
2. 系统建立文档记录并检查来源和格式。
3. 系统读取并整理文档内容。
4. 系统生成建议分类、标签和文档状态。
5. 文档通过基本检查后进入可查询状态。
6. 系统保存原文来源和处理记录。

异常流程：

- 文件格式不支持：提示支持的格式。
- 文件损坏或无法读取：记录失败原因并允许重试。
- 内容为空或明显异常：标记为待处理，不进入正常查询结果。
- Wiki 文档失效或无权访问：保留错误状态并提示重新授权或更换来源。

### UC-02：知识维护

目标：保证知识库内容持续有效。

主要流程：

1. 系统定期检查已接入 Wiki 文档是否更新。
2. 发现更新后创建同步任务。
3. 新版本处理完成后替换或并存旧版本索引。
4. 用户可查看同步状态和失败原因。
5. 维护人员可下线、恢复或重新处理文档。

业务规则：

- 原始文档必须保留来源。
- 文档更新不能产生重复的有效版本。
- 处理失败时，旧的有效版本是否继续可查询，需要在详细需求中确认。

### UC-03：产品知识查询

目标：帮助用户快速找到产品知识并理解相关内容。

主要流程：

1. 用户输入自然语言问题。
2. 用户可补充产品、版本、模块等条件。
3. 系统返回相关知识和自然语言答案。
4. 系统展示来源文档、章节或原文位置。
5. 用户可以继续追问或修正问题范围。

异常流程：

- 没有召回相关内容：明确提示未找到足够资料。
- 资料相互冲突：展示冲突来源，并提示用户确认版本或有效性。
- 问题信息不足：请求用户补充版本、模块、错误码等关键条件。

### UC-04：CDT 日志分析

目标：帮助问题处理人员基于 CDT 日志和问题描述形成辅助诊断报告。

主要参与者：SEG 技术支持、开发、测试。

输入：

- CDT 日志文件或日志压缩包。
- 用户填写的问题描述。
- 可选信息：产品版本、模块、部署方式、发生时间、变更记录和影响范围。

主流程：

1. 用户进入问题诊断并上传 CDT 日志。
2. 用户填写问题现象和已知环境信息。
3. 系统检查文件格式、大小和完整性。
4. 用户提交分析任务。
5. 系统整理日志中的时间、模块、错误、异常和关联信息。
6. 系统结合知识库中的相关资料和历史问题进行分析。
7. 系统生成诊断报告。
8. 用户查看报告、来源证据和下一步排查建议。
9. 用户可补充信息并重新分析或继续追问。

诊断报告至少包含：

- 问题摘要。
- 输入信息和分析范围。
- 关键日志片段或关键事件。
- 事件时间线。
- 影响模块和影响范围。
- 可能原因及其证据。
- 建议排查步骤。
- 建议验证方式。
- 待补充信息。
- 相关知识和历史案例引用。
- 结论可信程度或人工确认提示。

诊断结果必须区分：

- 已从输入或资料中直接观察到的事实。
- 基于证据形成的分析判断。
- 尚未确认的可能原因。
- 建议用户执行的下一步操作。

异常流程：

- 日志无法解析：显示失败原因，并允许用户重新上传或补充说明。
- 日志中没有明显异常：明确提示未发现有效异常，不生成确定性根因。
- 知识库没有相关案例：报告仍可基于日志生成，但标记缺少历史资料支持。
- 分析超时或服务失败：保留任务状态和错误信息，支持重新执行。
- 用户补充信息后重新分析：生成新的报告版本，保留历史报告。

## 7. 业务规则

1. 原始文档和原始日志是分析结果的事实依据，系统不得无依据修改其内容。
2. 知识库中的文档必须关联来源、版本和处理状态。
3. 一份文档可以有多个分类或标签，但不得因为多标签而重复保存多份原文。
4. 诊断报告必须标注证据来源。
5. 没有足够证据时，系统必须输出不确定性，而不是强行给出根因。
6. 诊断报告属于辅助分析结果，最终判断由专业人员完成。
7. 重新分析不能覆盖历史报告，应保留版本和输入信息。
8. 文档下线后，不应继续出现在正常查询结果中。
9. 处理失败的任务必须有可查询的失败原因。

## 8. 功能需求优先级

### Must Have

- 知识库文档接入和基本管理。
- Word/PDF/Excel 文件上传。
- 基础知识查询和来源展示。
- CDT 日志上传和问题描述填写。
- CDT 日志分析任务提交和状态展示。
- 诊断报告生成与查看。
- 处理失败提示和重新执行。

### Should Have

- 飞书 Wiki 定时更新。
- 文档分类和标签建议。
- 多轮追问和补充信息后重新分析。
- 历史报告查询。
- 混合检索和结果重排序。

### Could Have

- 报告导出。
- 用户对诊断结果进行反馈或修正。
- 将确认后的诊断报告沉淀为知识库案例。
- 文档重复检测和质量评分。

### V1 暂不包含

- 自动执行修复操作。
- 自动修改生产配置。
- 自动替代专家做最终判定。
- 多产品统一运营。

## 9. 非功能需求

- 可追溯性：答案和报告可以追溯到原始文档、日志或用户输入。
- 可用性：单个文档或诊断任务失败不能阻塞其他任务。
- 可恢复性：失败任务可以查看原因并重新处理。
- 安全性：上传文件需要进行类型、大小和压缩包安全检查。
- 可观测性：系统记录任务状态、耗时、失败原因和关键操作。
- 可扩展性：后续可以增加新的文档来源、日志格式和诊断场景。

## 10. V1 验收标准

### 知识库

- 用户可以接入或上传支持范围内的文档。
- 系统可以显示文档处理状态。
- 处理失败时可以显示原因并重新处理。
- 查询结果可以展示来源文档和原文位置。

### 产品知识查询

- 用户可以使用自然语言提问。
- 典型问题可以返回相关答案和来源。
- 无相关资料时系统会明确提示信息不足。
- 用户可以补充条件并继续查询。

### CDT 日志分析

- 用户可以上传支持范围内的 CDT 日志并填写问题描述。
- 系统可以显示分析任务进度和失败状态。
- 报告包含问题摘要、关键事件、可能原因、证据和排查建议。
- 报告能够区分事实、分析判断和待确认内容。
- 用户可以补充信息并生成新的报告版本。
- 系统不会自动执行修复操作。

## 11. 待确认问题

1. V1 支持的 CDT 日志具体格式、目录结构和压缩包类型是什么？
2. 单次上传的最大文件大小和日志保留时间是多少？
3. 第一批用于验证的历史日志和问题案例有多少？
4. 哪些角色可以提交诊断任务，哪些角色可以查看报告？
5. 诊断报告是否需要人工审核后才能被其他人查看？
6. 文档更新失败时，旧版本是否继续提供查询？
7. 知识库维护人员和问题诊断报告审核人由谁负责？
8. V1 选择哪些真实问题作为验收样本？
9. 如何衡量成功：定位耗时、报告采纳率、专家修改次数，还是其他指标？
