## 2. 当前有效业务目标

面向约 30 名部门内部用户建设单产品知识查询平台，让用户：

- 提交自己的飞书云文档链接或从可见文档中多选提交；
- 上传 Word、PDF、Excel 等本地文件；
- 由职责单一的 LLM 文档分类器自动分类；
- 在分类无法可靠判断时进入待确认，确认前不得参与知识查询；
- 通过自然语言提出问题；
- 可选使用产品、版本、文档类型缩小查询范围；
- 获得答案优先、带来源链接和必要结构化表格的回答；
- 在同一会话中继续自然语言追问；
- 对回答标记有帮助/无帮助，无帮助原因选填；
- 保存、归档、删除、导出或分享会话；
- 由管理员维护用户、产品、版本、分类、任务和系统运行状态。

V1 当前不包含：

- 问题诊断一级模块；
- CDT 日志分析用例；
- 诊断报告及飞书云文档导出；
- 复杂角色权限和文档级数据权限；
- 微服务拆分和复杂 Agent 编排。

问题诊断是后续业务模块；CDT 日志分析只是问题诊断下的一个具体用例。

## 3. 已确认的关键设计决策

| 主题 | 当前决定 |
|---|---|
| 系统形态 | 模块化单体，不使用微服务 |
| 后端 | Python + FastAPI |
| 前端 | React + TypeScript + Material UI（MUI 官方组件库） |
| 异步任务 | PostgreSQL 数据库任务表 + 独立 Worker，不引入消息队列 |
| 检索存储 | OpenSearch/Elasticsearch 类统一混合检索体系，同时承担 BM25、向量和元数据过滤 |
| 问答传输 | HTTP API + SSE 渐进返回，不使用 WebSocket |
| 模型接入 | LLM、Embedding、Rerank 均通过可配置 HTTP 服务接入，不在业务层区分本地或外部模型 |
| 文档分类 | LLM 分类器，分类配置从数据库读取；不是自治 Agent 编排 |
| 飞书同步 | 每日检查已提交文档的修改时间或 revision；发生变化才重新获取和更新，不全文比对 |
| 本地文件去重 | 以文件内容哈希为主，设计文档当前采用 SHA-256；早期讨论中的 MD5 不作为最终推荐 |
| 飞书去重 | 规范化后的底层文档 token 唯一识别 |
| 所有权 | 首位成功提交者拥有撤回/修改权；后续重复提交者不能撤回他人文档 |
| 文档版本 | 只让当前成功版本参与查询；新版本处理失败时继续使用旧成功版本 |
| 查询条件 | 产品、版本、文档类型是可选范围条件，不要求用户先选择问题类型 |
| 回答展示 | 答案优先；结构化信息使用表格；引用展示摘要和原文链接，不展开完整原文 |
| 来源冲突 | 先按来源优先级，再按更新时间；同优先级仍冲突时提示用户确认 |
| 会话数据 | 默认持久化；用户可以新建、归档、删除、导出和分享 |
| 初始规模 | 约 1,000 份文档、30 名用户；首轮按 3,000～5,000 份文档、10 个并发问答验证 |

### 8.3 “自动分类”与“用户可修改”边界

当前理解：

- 默认自动分类；
- 用户提交时不手动选择分类；
- 分类成功后允许提交者从详情页纠正；
- 分类无法判断时由管理员或指定处理人确认；
- 纠正后需要更新元数据索引，正文和切片规则未变时不重新 Embedding。

待确认：普通提交者是否可以处理待确认，还是仅管理员可以。
