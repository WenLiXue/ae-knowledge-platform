## 3. 下一步任务（新会话主目标）

按 DD-19 §20，**完成 Phase 3 剩余部分**（分类器），不要跨 Phase。

### 3.1 分类器（§8）—— `backend/app/classify/`（建议）
1. `schemas.py`：`ClassificationOutput`（§8.1，relevance/relevance_confidence/product_code/product_version_code/document_type_code/product_form_code/is_domestic/module_name/business_topic/keywords/summary/field_confidence/evidence/missing_fields/reason_summary）+ `FieldEvidence`。
2. `input_builder.py`（§8.2）：按预算从 ParsedDocument 选块（标题/目录/一二级标题/摘要/章节首段/表格表头+代表行/命中术语上下文），每块带稳定 locator；`input_hash = SHA-256(content_sha256 + config_revision + model_key + model_revision + prompt_revision + input_builder_revision)`。
3. `prompts.py`（§8.3）：系统消息声明正文不可信；正文放独立结构化边界；只允许 JSON；code 必须来自当前启用 taxonomy（读 `knowledge.document_types` ENABLED）；未知返回 null；evidence locator 必须来自输入。
4. `validator.py`（§8.4）：JSON → Pydantic → 置信度 → code 合法 → 产品版本归属 → locator → 长度/数量 → null 语义；首次失败允许一次带结构化错误的修复调用；仍失败进任务重试。
5. `service.py` 决策：RELEVANT（置信度≥0.80 且有效相关证据）、IRRELEVANT（≥0.90 且有效无关证据）、否则 UNCERTAIN；UNCERTAIN 不建 Chunk，来源/版本进待确认。
6. 事务边界（§8.5）：模型 HTTP 调用不得持有 DB 事务/行锁；短事务读版本+配置+input_hash → 事务外调模型 → 短事务锁版本插入 ClassificationResult → 领域服务应用 metadata/状态 → 创建下一阶段任务。
7. **接线 CLASSIFY**：`pipeline.py` 的 `_mock_classify` 改为当 `feature_real_classification=True` 走真实分类（读取 ParsedDocument → 分类 → 写 `classification_results` + `document_metadata` → RELEVANT 进 CHUNK、UNCERTAIN 置 PENDING_CONFIRMATION、IRRELEVANT 来源 OFFLINE）；Flag 关闭时保持现有 mock。模型不可用**禁止默认相关**。

## 4. 关键约定与坑（务必读）

1. **GateGuard hook**：每个文件**首次**编辑/新建前，必须先陈述事实（调用方/受影响 API/数据结构/用户指令原文），GateGuard 会拒绝一次，**重试即可成功**。不要困惑，重试是预期流程。
2. **对象存储**：本地 `LocalObjectStore`（`backend/app/storage/local.py`）。`test_worker_restart_continues_pipeline` 已改为**两个 runner 共享同一 store**（生产对象存储跨重启持久，raw/parsed 对象可读）——后续写真实分类时 PARSE 产物需可读。
3. **`app/parsing/` 产出**：`ParsedDocument` 含 `elements`（heading/paragraph/list_item/table/sheet_region），每元素 `element_id`（`el-{:04d}`）、`heading_path`、`locator`；`stats.element_count`。blocks 形式标题是**兄弟**（无层级）；raw_content 是 Markdown。
4. **`app/llm/`（DD-20）**：`resolve_service_model(db, service_type)` → `ResolvedModel(provider, base_url, model_name, api_key, config_revision)`。ServiceType 含 `DOCUMENT_CLASSIFICATION`。分类器用它与 `app/model_gateway.create_gateway` 组合；**不要读前端表单/拼供应商 URL**。
5. **Model Gateway 用法**：
   ```python
   from app.llm.runtime import resolve_service_model
   from app.model_gateway import create_gateway, ChatRequest, GatewayError
   model = resolve_service_model(db, "DOCUMENT_CLASSIFICATION")  # 未配置抛 LLMConfigError
   gateway = create_gateway(model)  # 传 http_client=... 可注入测试
   resp = gateway.chat(ChatRequest(model=model.model_name, messages=[...]))
   ```
   错误已分类；`GatewayError.retryable` 决定任务是否重试。
6. **日志**：正文、Prompt、Token、API Key 一律不进日志（§7/§17）。分类日志只记 id/阶段/耗时/用量/稳定错误码。
7. **迁移**：`alembic revision -m "..."` 生成骨架（down_revision 自动取当前 head），再手写。新表在 `knowledge` schema，UUID，`created_at/updated_at`，必要索引/FK；`migrations/env.py` 管理 auth/knowledge/tasking/platform 四个 schema。**每次迁移后测试库实测 upgrade/downgrade/往返**。
8. **测试基建**：`conftest.py` 每会话从空库跑全部迁移、每测试前 TRUNCATE 业务表（含 document_types）——目录测试需自行 seed（参考 `_seed_document_types`）。
9. **前端**：Phase 3 无前端改动；Phase 6 才替换 `frontend/src/api/conversations.ts` 的会话 Mock。当前 QueryComposer 已接真实目录。
