# AE 内部知识平台 V1 详细设计总纲

版本：V0.1  
状态：讨论稿  
日期：2026-08-17  
上游基线：《产品知识查询 V1 需求基线》《AE 内部知识平台 V1 概要设计 V1.0》

## 1. 文档目标

本套详细设计将概要设计中的模块、数据和流程展开为可编码、可测试、可部署的实现契约。目标读者为产品、前端、后端、测试和运维人员。

详细设计完成后，开发不需要自行猜测以下事项：

- 对象有哪些状态以及如何转换；
- 数据写入哪些表，事务在哪里结束；
- API 输入、输出、错误和幂等规则；
- 文档任务失败、中断、重复执行后如何恢复；
- RAG 的召回、排序、证据和引用如何衔接；
- 页面在正常、空数据、加载、失败和降级状态下如何展示；
- 每项设计由什么测试证明实现正确。

## 2. 设计范围

V1 详细设计包含知识库管理、智能问答和系统管理三个业务模块，以及认证、文档治理、LLM 分类器、混合检索、异步任务、对象存储和外部服务适配等技术能力。

不包含问题诊断模块、CDT 日志分析、诊断报告、复杂角色权限、文档级数据权限和产品级操作审计。

## 4. 统一编号

- 需求：`FR-模块-序号`，例如 `FR-KB-001`。
- 设计决定：`ADR-序号`，例如 `ADR-001`。
- 领域对象：`DM-对象名`。
- 状态机：`SM-对象名`。
- API：`API-模块-序号`。
- 页面：`UI-模块-序号`。
- 交互流程：`UX-FLOW-序号`。
- 测试用例：`TC-模块-序号`。
- RAG 评测样本沿用 `KQ-001`～`KQ-032`。

## 5. 追踪规则

每个可观察业务行为至少形成以下链路：

```text
需求 FR
  → 领域命令/状态机 SM
  → 数据表与事务 DB
  → API
  → 页面/交互 UI 或 UX-FLOW
  → 测试用例 TC
```

纯后台行为可以没有页面，但必须对应任务、日志、指标和测试。页面按钮不得没有业务命令和 API；API 不得绕过领域状态机直接修改状态。

## 6. 全局不变量

1. PostgreSQL 是业务状态唯一事实来源，搜索索引是可重建派生数据。
2. 一个知识来源最多只有一个当前可查询版本。
3. 新版本完全处理成功前，不改变当前可查询版本。
4. 文档下线优先于并发同步，同步成功不能自动恢复下线文档。
5. 同一飞书 token 或本地文件 MD5 不得产生重复有效来源。
6. 任务可以重复投递，但业务结果必须幂等。
7. 分类器和生成模型不得补写无来源的内部产品事实。
8. 回答中的引用只能指向本次证据集合中的文档版本和切片。
9. 会话删除为逻辑删除；分享内容是创建时快照。
10. V1 允许配置备用模型，但必须标记实际使用的模型和切换原因，不得静默掩盖外部模型故障。

## 7. 决策状态

- `已确认`：来自需求或概要设计基线，详细设计不得擅自修改。
- `推荐基线`：为继续设计提出的工程选择，评审确认后转为已确认。
- `待验证`：需要样本、性能测试或部署环境验证。
- `待确认`：业务或组织输入缺失，会实质影响实现。

## 8. 原型设计要求

原型是正式详细设计分册，不是效果图附件。每个页面必须包含页面目的、进入条件、字段、操作、状态、跳转、错误、空数据和接口映射。

智能问答原型必须覆盖正常回答、流式生成、多来源引用、结构化表格、追问、部分依据、无依据、来源冲突、Embedding 降级、Rerank 降级、LLM 失败、中止生成和历史来源下线。

文档详情原型必须覆盖处理中、可查询、待确认、失败、新版同步失败、已下线和恢复处理中。

## 9. 详细设计完成标准

- 所有 V1 Must Have 需求都有设计和测试映射；
- 核心对象具有状态机、并发规则和恢复路径；
- 数据表、API 和页面字段命名一致；
- 外部依赖都有超时、错误分类、重试或不重试规则；
- 所有异步写操作都有幂等和中断恢复设计；
- RAG 参数具有初始值、配置方式和黄金问题集验证方法；
- 页面正常和异常状态均有原型；
- 部署、备份和恢复能够由运维按文档执行；
- 未决项有负责人、影响和关闭条件。
