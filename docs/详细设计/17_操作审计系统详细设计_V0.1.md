# AE 内部知识平台——操作审计系统详细设计

版本：V0.1  
状态：建议稿  
文档编号：DD-17  
日期：2026-08-25  
依赖：DD-03、DD-08、DD-11、DD-12、DD-14

## 1. 背景与目标

当前工程已经具备管理员标识、登录会话、管理配置接口和 PostgreSQL，但尚无可用的审计领域模型、写入服务、查询 API 与前端页面。仓库中已有 `platform.audit_logs` 迁移草稿和审计页面交互原型，可作为实现输入，不代表审计链路已经完成。

本系统面向平台管理员和故障调查人员，解决关键操作不可追溯的问题，使系统能够回答：谁在何时、通过什么入口、对哪个业务对象执行了什么操作，结果如何，关键字段发生了哪些变化。

设计目标：

- 关键业务变更成功时，业务数据与成功审计记录原子提交；
- 权限拒绝、参数校验失败和业务冲突等失败操作可追踪；
- 审计记录只追加，不提供业务 API 修改或删除；
- 支持按时间、操作者、模块、动作、对象和结果筛选及导出；
- 不记录密码、Token、密钥、Cookie、文档正文、问题正文、答案正文和完整异常堆栈；
- 在当前单体架构和目标规模下实现，不新增消息队列或独立审计服务。

非目标：

- 不把运行日志、指标、链路追踪替换为审计日志；
- 不记录所有 GET 请求；只记录敏感读取和导出；
- 不建设完整 SIEM、复杂 RBAC 或文档级权限体系；
- 不以审计表作为业务状态恢复或事件溯源数据源。

## 2. 验收标准

| 编号 | 可观察行为 |
|---|---|
| AC-AUD-001 | 管理员可分页查询审计记录，并按时间、操作者、模块、动作、对象类型、结果筛选 |
| AC-AUD-002 | 每个已纳入范围的成功变更都存在且仅存在一条对应成功记录 |
| AC-AUD-003 | 业务事务回滚时不留下成功记录；业务成功时不会缺少成功记录 |
| AC-AUD-004 | 权限拒绝、业务校验失败和外部依赖失败记录稳定错误码，不记录敏感异常详情 |
| AC-AUD-005 | 详情展示操作者快照、请求关联号、来源、对象、结果及白名单化变更前后值 |
| AC-AUD-006 | 导出与当前筛选条件一致，导出行为本身被审计，且有条数和时间范围上限 |
| AC-AUD-007 | 普通用户不能读取或导出审计日志 |
| AC-AUD-008 | 应用账号无 UPDATE/DELETE 审计表权限，且可验证记录链完整性 |

## 3. 审计范围

### 3.1 第一阶段必须记录

| 模块 | 动作示例 | 结果 |
|---|---|---|
| `AUTH` | `auth.login`、`auth.logout`、`auth.feishu.bind`、`auth.feishu.unbind` | 成功、失败、拒绝 |
| `USER` | `user.create`、`user.update`、`user.enable`、`user.disable`、`user.role.change` | 成功、失败、拒绝 |
| `DOCUMENT` | `document.import`、`document.metadata.update`、`document.offline`、`document.retry`、`classification.confirm` | 成功、失败、拒绝 |
| `TASK` | `task.retry`、`task.cancel`、`task.retry_batch` | 成功、失败、拒绝 |
| `CONFIG` | 目录项增改/启停、来源优先级修改、`config.llm.update`、配置发布/回滚 | 成功、失败、拒绝 |
| `AUDIT` | `audit.view_detail`、`audit.export` | 成功、失败、拒绝 |

知识查询默认不逐次写入操作审计表。查询统计属于运营指标；只有查看受限对象、批量导出或未来权限策略要求时，才记录敏感读取事件，并且只保存会话/答案 ID 和结果元数据。

### 3.2 操作者类型

- `USER`：登录用户；保存 `actor_user_id` 和显示名/账号快照；
- `SYSTEM`：系统启动、维护任务；`actor_user_id` 为空，保存稳定 `actor_key`；
- `WORKER`：异步任务；保存 Worker 标识，并通过 `causation_id` 关联触发它的用户操作；
- `SERVICE`：未来系统间调用；保存客户端标识，不保存凭据。

用户被删除或改名后，历史记录仍通过快照可读；外键使用 `ON DELETE SET NULL`，不能因删除用户而删除审计历史。

## 4. 事件模型

一次审计事件由以下语义组成：

```text
Actor + Source + Action + Target + Outcome + Change + Correlation
```

- Actor：操作者身份及当时的显示快照；
- Source：入口类型、IP、User-Agent；
- Action：稳定动作码，不使用中文文案作为查询条件；
- Target：对象类型、对象 ID、对象名称快照；
- Outcome：`SUCCESS`、`FAILURE` 或 `DENIED`；
- Change：白名单字段的变更前后值；
- Correlation：`request_id`、`trace_id`、`causation_id` 和幂等键摘要。

### 4.1 写入时序

成功操作：

```text
HTTP Router → 认证/授权 → Application Service
                         → 修改业务聚合
                         → 构造 SUCCESS 审计事件
                         → 同一数据库事务 commit
                         → 返回响应
```

失败操作：

```text
HTTP Router / Service 抛出稳定业务异常
  → 回滚业务事务
  → 使用独立短事务写 FAILURE 或 DENIED
  → 返回原始业务错误
```

禁止先提交业务数据、再尽力写成功审计。对 PostgreSQL 内的业务变更，成功审计与业务变更必须共享事务。外部副作用无法与数据库原子提交时，记录 `external_operation_id` 和 `UNKNOWN/SUCCESS/FAILURE` 的最终确认事件；调用超时不能武断记为失败。

### 4.2 重试与幂等

- 每次实际请求都有独立 `event_id`，重复请求不会覆盖旧事件；
- `request_id + action + target` 用于调查关联，不强制唯一；
- 有 `Idempotency-Key` 时只保存其 SHA-256 摘要，不保存原值；
- 命中幂等缓存的重复请求记录 `detail.execution=REPLAYED`，不伪装成再次执行业务变更；
- 批量操作写一条批次事件和每个失败项的有限摘要，避免无限放大日志量。

## 5. 数据设计

现有迁移草稿只有 `user_id/action/resource/detail/ip/user_agent/created_at`，不足以可靠支持结果筛选、失败原因、操作者快照、请求关联、数据留存与防篡改。建议在正式合并迁移前调整为：

### 5.1 `platform.audit_logs`

| 字段 | 类型 | 规则 |
|---|---|---|
| `id` | UUID | 主键，应用生成 UUIDv7；若当前依赖不支持则先用 UUIDv4 |
| `occurred_at` | timestamptz | 事件发生时间，数据库默认 `now()` |
| `actor_type` | varchar(16) | `USER/SYSTEM/WORKER/SERVICE` |
| `actor_user_id` | UUID nullable | FK `auth.users(id) ON DELETE SET NULL` |
| `actor_key` | varchar(128) nullable | 系统、Worker 或服务稳定标识 |
| `actor_name` | varchar(128) | 操作者显示名快照 |
| `actor_account` | varchar(320) nullable | 用户名或脱敏邮箱快照 |
| `module` | varchar(32) | 稳定模块码 |
| `action` | varchar(128) | 稳定动作码，如 `config.llm.update` |
| `target_type` | varchar(64) nullable | 业务对象类型 |
| `target_id` | varchar(128) nullable | 业务对象 ID |
| `target_name` | varchar(256) nullable | 对象名称快照 |
| `outcome` | varchar(16) | `SUCCESS/FAILURE/DENIED` |
| `error_code` | varchar(64) nullable | 稳定错误码，不保存堆栈 |
| `summary` | varchar(512) | 面向管理员的安全摘要 |
| `changes` | JSONB | 字段级 `{field, before, after}` 列表，默认 `[]` |
| `metadata` | JSONB | 经过白名单过滤的补充元数据，默认 `{}` |
| `request_id` | varchar(64) | 每个入口请求必填；Worker 使用任务执行 ID |
| `trace_id` | varchar(64) nullable | 与链路追踪关联 |
| `causation_id` | UUID nullable | 触发当前事件的审计事件 ID |
| `source_type` | varchar(16) | `WEB/API/WORKER/SCHEDULER` |
| `source_ip` | inet nullable | 只信任配置过的反向代理转发头 |
| `user_agent` | varchar(256) nullable | 截断并清除控制字符 |
| `prev_hash` | char(64) nullable | 同一哈希分区上一条记录摘要 |
| `record_hash` | char(64) | 规范序列化后 HMAC-SHA256 |
| `schema_version` | smallint | 事件 Schema 版本，初始为 1 |

`changes` 只记录允许审计的业务字段。LLM 配置可记录模型名、Endpoint、超时、重试和“密钥是否配置”的变化，绝不记录 API Key 密文或明文。

### 5.2 索引与分区

初始规模可使用普通表，建立：

- `(occurred_at DESC, id DESC)`：默认游标分页；
- `(actor_user_id, occurred_at DESC)`；
- `(module, outcome, occurred_at DESC)`；
- `(action, occurred_at DESC)`；
- `(target_type, target_id, occurred_at DESC)`；
- `(request_id)`。

不为任意 JSONB 内容建立宽泛 GIN 索引。数据超过约一千万行或维护窗口不可接受时，再按月对 `occurred_at` 原生分区；不要在首版提前增加分区运维成本。

### 5.3 不可篡改与留存

- 业务应用数据库角色只授予 `SELECT/INSERT`，撤销 `UPDATE/DELETE/TRUNCATE`；
- HMAC 密钥由运行环境提供，不能存入数据库；按自然日或月建立哈希链，定期把链头摘要保存到独立备份/对象存储；
- 数据库超级用户仍可篡改，因此“只追加”不等于绝对不可篡改；哈希链用于发现事后修改；
- 默认在线保留 180 天、归档保留 2 年；最终期限需由安全/法务确认；
- 清理只能由受控运维作业按分区/时间执行，记录归档清单、条数和链头摘要，不提供产品删除按钮。

## 6. 后端设计

建议新增：

```text
backend/app/audit/
├── api.py          # 管理员查询、详情、导出
├── context.py      # request_id、来源、操作者上下文
├── models.py       # AuditLog ORM
├── schemas.py      # 查询和响应 Schema
├── service.py      # 事件构造、脱敏、哈希、查询
└── policy.py       # 动作目录和字段白名单
```

### 6.1 接入方式

不采用“记录所有请求”的全局中间件作为主方案，因为中间件不知道领域对象、真实变更前后值和事务结果。采用两层组合：

1. 中间件只生成/透传 `X-Request-ID`，提取可信来源信息；
2. 应用服务在业务规则校验后调用 `audit.record_success(db, event)`，与业务写入共享 `Session`；
3. 统一异常映射层根据显式 `AuditIntent` 记录 `FAILURE/DENIED`；没有动作意图的 404、静态资源错误不写审计。

当前 `config.service` 中方法自行 `commit()`，会阻碍“业务 + 审计”原子提交。实施时应把已纳入审计的服务改为只 `flush()`，由应用服务/Unit of Work 在加入审计记录后统一 `commit()`。这是接入审计前的必要事务边界调整，不应只在 Router 中追加第二次提交。

### 6.2 动作目录

`policy.py` 维护代码级注册表：动作码、模块、目标类型、允许变更字段、是否记录失败、风险等级。未知动作在测试/开发环境直接拒绝，在生产环境记录运行错误并拒绝写入，避免自由文本污染查询口径。

脱敏规则采用“默认拒绝 + 白名单允许”，并递归拒绝字段名匹配：`password`、`secret`、`token`、`cookie`、`authorization`、`api_key`、`content`、`body`、`prompt`。字符串有单字段和事件总大小上限；超限保存截断标记与原值摘要。

### 6.3 查询 API

| 方法与路径 | 说明 |
|---|---|
| `GET /api/v1/admin/audit-logs` | 游标分页列表和组合筛选 |
| `GET /api/v1/admin/audit-logs/{event_id}` | 详情；读取详情本身可按策略审计 |
| `GET /api/v1/admin/audit-logs/summary` | 指定时间窗口的模块/结果计数 |
| `POST /api/v1/admin/audit-exports` | 创建导出任务，返回 202 |
| `GET /api/v1/admin/audit-exports/{export_id}` | 查询导出状态 |
| `GET /api/v1/admin/audit-exports/{export_id}/download` | 短时认证下载 |

列表参数：`start_at`、`end_at`、`actor_user_id`、`module`、`action`、`target_type`、`target_id`、`outcome`、`keyword`、`cursor`、`limit`。`limit` 默认 50、最大 200，时间范围默认最近 24 小时、单次最大 90 天。关键词只匹配日志编号、操作者快照和对象快照，不扫描 JSON 正文。

导出使用异步任务，最大 100,000 条或 90 天；导出文件使用 UTF-8 BOM CSV，公式注入字符 `= + - @` 前加单引号，24 小时后删除。导出文件不包含 `changes` 的未筛选 JSON，可提供受限的字段级明细列。

## 7. 前端设计

复用 `docs/prototypes/visual-directions/audit-logs.html` 的列表、筛选、概要和详情抽屉，不把原型中的静态数量或本地 CSV 逻辑直接带入实现。

- 路由：`/admin/audit-logs`，仅 `is_admin=true` 展示入口，后端仍必须强制鉴权；
- 默认最近 24 小时，筛选条件同步 URL query，刷新和分享链接后保持；
- 表格显示时间/编号、操作者、模块、动作、对象、结果、来源 IP；
- 详情抽屉显示安全摘要、请求编号、变更字段和稳定错误码；
- 大数据导出展示异步任务状态，不在浏览器拼接全部 CSV；
- 未知模块/动作码显示原始码，保证后端先发布新枚举时旧前端不崩溃。

## 8. 安全与隐私

- 查询、详情和导出仅管理员访问；未来可拆分 `AUDIT_VIEWER`，当前不提前扩展角色模型；
- 管理接口保留现有 Cookie 认证，同时应按 DD-12 补齐 CSRF 防护；
- 来源 IP 只从实际连接地址或可信代理层读取，不能直接信任任意 `X-Forwarded-For`；
- 登录失败不保存用户输入的密码；账号可标准化后保存摘要或部分掩码，避免账号枚举泄露；
- 外部错误只保存内部稳定错误码和清洗后的短摘要；完整堆栈进入受控运行日志并通过 `request_id` 关联；
- 审计导出属于高风险操作，应记录筛选范围、导出条数、文件摘要和下载者，不记录下载 URL；
- 审计数据不进入 RAG 索引，也不作为模型提示词输入。

## 9. 异常、一致性与恢复

| 场景 | 期望行为 |
|---|---|
| 业务校验失败 | 回滚业务事务，独立写 `FAILURE`，返回原错误 |
| 权限校验失败 | 不执行领域命令，写 `DENIED`，不泄露目标详情 |
| 成功审计写入失败 | 整个业务事务失败；返回稳定 `AUDIT_WRITE_FAILED`，告警 |
| 失败审计写入失败 | 不覆盖原业务错误；输出安全运行日志和指标并告警 |
| 外部调用超时 | 记录 `UNKNOWN` 元数据或失败事件，后续确认结果可追加关联事件 |
| Worker 崩溃 | 原任务/attempt 状态用于恢复；重试产生新事件并通过 causation 关联 |
| 应用重启 | 已提交事件不受影响；未提交业务与审计一并回滚 |
| 哈希链校验失败 | 只读冻结相关导出，发出高优先级告警并启动调查，不自动修复历史 |

审计不是主业务的“尽力而为”日志。纳入强审计范围的成功操作在审计不可写时应失败关闭（fail closed）；普通查询等非审计操作可继续服务，避免审计故障扩大为全站不可用。

## 10. 测试设计

### 10.1 单元测试

- 动作注册表拒绝未知动作；
- 字段白名单、递归脱敏、长度限制和控制字符清理；
- 规范 JSON 序列化和 HMAC 哈希可重复；
- IP/代理头可信边界；
- CSV 公式注入防护；
- 游标编码、时间范围和最大 limit 校验。

### 10.2 数据与应用服务测试

- 业务变更和 SUCCESS 审计同事务成功；
- 人为制造审计插入失败，业务数据不提交；
- 业务异常回滚后只有 FAILURE/DENIED 记录；
- 同一幂等请求重放不重复改变业务状态，事件标记 `REPLAYED`；
- 并发配置修改保留各自请求记录，失败方为 `VERSION_CONFLICT`；
- 删除/停用用户不破坏历史操作者快照；
- 数据库应用角色不能 UPDATE/DELETE/TRUNCATE 审计表；
- 修改历史记录后哈希链校验能够发现异常。

### 10.3 API 与 E2E

- 普通用户查询、详情和导出均为 403，并产生适当拒绝记录；
- 多条件筛选、跨时区边界、游标翻页无重复遗漏；
- 详情不返回密钥和正文；
- 导出筛选与列表一致、超限拒绝、过期文件不可下载；
- 前端正常、空、加载、失败、未知枚举和导出处理中状态；
- 原型中的详情抽屉和只读约束在真实 API 下保持。

## 11. 实施顺序与回滚

1. 产品确认审计范围、留存期和审计查看权限；
2. 在尚未发布的迁移草稿上补齐字段、约束和索引，新增 ORM 与动作目录；
3. 实现 request context、脱敏、哈希和查询服务；
4. 先接入 LLM 配置、目录配置、来源优先级、登录/解绑等高风险操作；
5. 调整服务事务边界，完成原子性故障测试；
6. 上线只读查询 API 与前端页面；
7. 上线异步导出、留存和链校验作业；
8. 观察漏记率、写入失败率、表增长和查询延迟后扩展到文档/任务全量动作。

灰度期间可通过配置开关隐藏查询入口，但不能在已要求强审计的操作上静默关闭写入。回滚应用时保留新增表和已写记录；旧版本不读取审计表即可。数据库迁移 downgrade 会删除历史，不应在生产执行，改用向前修复迁移。

## 12. 监控指标

- `audit_write_total{action,outcome}`；
- `audit_write_failure_total{stage}`；
- `audit_write_duration_seconds`；
- `audit_query_duration_seconds` 和慢查询数；
- `audit_export_total{status}`、导出条数和文件大小；
- 最近一次哈希链校验时间、校验记录数和失败数；
- 估算表大小、日增记录数和最老在线记录时间。

告警优先级：成功审计写入失败和哈希校验失败为高优先级；失败审计写入失败、导出失败和清理失败为中优先级。

## 13. 待确认项

1. 审计能力作为 V1.1 还是当前 V1 的上线门槛；
2. 在线与归档留存期限是否采用 180 天/2 年；
3. 是否允许所有管理员导出，还是需要独立审计查看角色；
4. 登录失败账号标识允许保存到什么粒度；
5. 生产是否已有可信反向代理、对象存储和独立归档账号；
6. 哪些“读取”属于敏感读取，需要进入第一阶段动作目录。
