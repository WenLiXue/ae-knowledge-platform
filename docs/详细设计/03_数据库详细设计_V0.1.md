# DD-03 PostgreSQL 数据库详细设计

版本：V0.1  
状态：讨论稿，待 Alembic DDL 验证  
日期：2026-08-17  
数据库基线：PostgreSQL 16 或公司受支持的更高版本

## 1. 设计目标

数据库保存系统全部权威业务状态，支撑身份、知识来源、文档版本、可恢复任务、会话问答、引用、反馈、分享和配置。OpenSearch/Elasticsearch 与对象存储均不是业务状态的唯一事实来源。

本章定义逻辑表、关键字段、约束、索引和事务。SQL 片段用于表达设计语义，尚未作为可执行迁移脚本验证；正式 DDL 由 Alembic 生成并在 Testcontainers PostgreSQL 中验证。

## 2. 通用规范

### 2.1 命名与类型

- 数据库、表和字段使用 `snake_case`；
- 主键统一使用 UUID v4，由应用生成；
- 时间统一使用 `timestamptz`，应用和数据库按 UTC 保存；
- 金额之外不使用无必要的 `numeric`；计数和序号使用 `integer/bigint`；
- 状态使用 `varchar` + `CHECK`，不使用 PostgreSQL 原生 ENUM，降低状态演进迁移成本；
- 可搜索短文本使用 `varchar(n)`，正文使用 `text`；
- JSONB 只保存结构不稳定的扩展数据、快照和外部响应摘要，不能替代核心关系字段；
- Token、密码和密钥不以明文保存。

### 2.2 通用字段

业务主表通常包含：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | `uuid` | 主键 |
| `created_at` | `timestamptz` | 创建时间 |
| `updated_at` | `timestamptz` | 最近业务更新时间 |
| `row_version` | `integer` | 乐观锁版本，初始为 1 |

只有需要逻辑删除的对象增加 `deleted_at`。知识来源下线、账号停用和会话归档都有独立业务状态，不能复用 `deleted_at`。

### 2.3 外键策略

- 业务数据默认 `ON DELETE RESTRICT`；
- 明确属于父对象、且父对象允许物理删除的临时数据才使用 `CASCADE`；
- V1 核心业务数据不提供物理删除，因此不依赖级联删除维持一致性；
- 对外部资源只保存系统内引用和快照，不建立外部数据库外键。

## 3. Schema 划分

V1 仍使用一个 PostgreSQL 数据库。为便于模块边界和权限管理，建议使用逻辑 Schema：

| Schema | 内容 |
|---|---|
| `auth` | 用户、飞书身份、凭据和登录会话 |
| `knowledge` | 来源、版本、元数据、切片和分类配置 |
| `tasking` | 任务与执行 attempt |
| `conversation` | 会话、消息、回答、引用、反馈、分享和导出 |
| `platform` | 系统配置版本和运行辅助数据 |

如果公司 DBA 规范要求单一 `public` Schema，可以使用统一表名前缀替代，但模块归属不变。

## 5. 知识来源与版本表

### 5.1 `knowledge.knowledge_sources`

| 字段 | 类型 | 约束/说明 |
|---|---|---|
| `id` | `uuid` | PK |
| `owner_user_id` | `uuid` | FK → auth.users |
| `source_type` | `varchar(32)` | `FEISHU` / `LOCAL_FILE` |
| `canonical_key` | `varchar(512)` | 飞书底层 token 或本地 `md5:<hex>` |
| `display_name` | `varchar(512)` | 当前展示标题 |
| `status` | `varchar(32)` | `PROCESSING` / `PENDING_CONFIRMATION` / `QUERYABLE` / `FAILED` / `OFFLINE` |
| `update_status` | `varchar(32)` | `IDLE` / `CHECKING` / `UPDATING` / `FAILED` |
| `current_version_id` | `uuid` | 可空，FK → document_versions，延迟建立 |
| `pending_version_id` | `uuid` | 可空，当前处理中的新版本 |
| `submitted_at` | `timestamptz` | 非空 |
| `offlined_at` | `timestamptz` | 可空 |
| `offline_reason` | `text` | 可空 |
| `last_sync_checked_at` | `timestamptz` | 可空 |
| `last_sync_error_code` | `varchar(128)` | 可空 |
| `created_at/updated_at/row_version` | 通用 | 非空 |

关键约束：

- `current_version_id` 必须属于本来源且版本为 READY，此跨表规则由事务和约束触发器二选一实现；优先应用事务 + 集成测试，不先引入复杂触发器；
- `status='QUERYABLE'` 时 `current_version_id IS NOT NULL`；
- `status='OFFLINE'` 时不限制 current version，便于历史引用和恢复。

重复来源使用部分唯一索引：

```sql
CREATE UNIQUE INDEX uq_active_source_key
ON knowledge.knowledge_sources (source_type, canonical_key)
WHERE status <> 'OFFLINE';
```

这允许旧来源下线后由其他用户重新提交，同时防止两个非下线来源并存。

### 5.7 `knowledge.classification_results`

该表保存分类器每次可复现运行的证据；`document_metadata` 保存当前被业务采用的数据，两者不能合并。

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | `uuid` | PK |
| `version_id` | `uuid` | FK → document_versions |
| `config_revision` | `bigint` | FK → platform.config_revisions |
| `model_key` | `varchar(128)` | 模型逻辑键 |
| `model_revision` | `varchar(128)` | 可空，服务商模型版本 |
| `prompt_revision` | `varchar(64)` | 非空 |
| `input_builder_revision` | `varchar(64)` | 非空 |
| `input_hash` | `char(64)` | 内容、配置、模型、Prompt 和输入构造版本联合哈希 |
| `status` | `varchar(32)` | `VALIDATED` / `INVALID` / `FAILED` |
| `relevance` | `varchar(32)` | 可空，`RELEVANT` / `IRRELEVANT` / `UNCERTAIN` |
| `relevance_confidence` | `numeric(5,4)` | 可空 |
| `output_json` | `jsonb` | 校验后的完整结构化输出；非法输出不保存正文 |
| `evidence_json` | `jsonb` | locator 与短证据摘录 |
| `latency_ms` | `integer` | 可空 |
| `token_usage` | `jsonb` | 可空，不同服务商统一映射后的用量 |
| `error_code/error_summary` | 字符串/文本 | 可空，不保存敏感正文 |
| `created_at` | `timestamptz` | 非空 |

约束与索引：

- `UNIQUE(version_id, input_hash)`，保证相同输入幂等；
- `(version_id, created_at DESC)`，用于查看历史运行；
- `CHECK(relevance_confidence BETWEEN 0 AND 1)`；
- `VALIDATED` 结果必须具有 relevance 和 output_json；
- 当前采用结果由应用按“成功应用到 document_metadata 的 result_id”关联，建议在 `document_metadata` 增加可空 `classification_result_id` FK；人工修改后的元数据仍保留该初始结果，同时在字段来源中标记 `MANUAL`。

| `last_error_category` | `varchar(32)` | 可空 |

部分唯一索引阻止同一业务任务并发存在：

```sql
CREATE UNIQUE INDEX uq_open_task_idempotency
ON tasking.processing_tasks (idempotency_key)
WHERE status IN ('PENDING', 'RUNNING', 'RETRY_WAIT');
```

领取索引：

```sql
CREATE INDEX ix_task_claim
ON tasking.processing_tasks (priority, scheduled_at, created_at)
WHERE status IN ('PENDING', 'RETRY_WAIT');
```

## 9. 核心事务设计

### 9.1 提交知识来源

事务内：

1. 规范化 token 或计算 MD5；
2. 插入 knowledge_source；
3. 插入来源详情和首个 document_version；
4. 插入首个 processing_task；
5. 提交。

遇到 `uq_active_source_key` 冲突时回滚新记录，查询并返回已有来源摘要。不得把冲突转换为“后提交用户成为共同所有者”。

### 9.2 激活文档版本

设计伪 SQL：

```sql
BEGIN;
SELECT * FROM knowledge.knowledge_sources
WHERE id = :source_id FOR UPDATE;

-- 应用校验 source.status != OFFLINE，目标版本属于来源且 status=READY
UPDATE knowledge.knowledge_sources
SET current_version_id = :new_version_id,
    pending_version_id = NULL,
    status = 'QUERYABLE',
    update_status = 'IDLE',
    row_version = row_version + 1,
    updated_at = now()
WHERE id = :source_id AND status <> 'OFFLINE';

UPDATE knowledge.document_versions
SET status = 'SUPERSEDED', updated_at = now()
WHERE id = :old_version_id AND id <> :new_version_id;

INSERT INTO tasking.processing_tasks (...旧索引清理任务...);
COMMIT;
```

外部索引调用发生在进入激活事务之前。旧索引清理由事务中创建的任务异步完成。

### 9.3 Worker 领取任务

设计伪 SQL：

```sql
BEGIN;
WITH picked AS (
  SELECT id
  FROM tasking.processing_tasks
  WHERE status IN ('PENDING', 'RETRY_WAIT')
    AND scheduled_at <= now()
  ORDER BY priority, scheduled_at, created_at
  FOR UPDATE SKIP LOCKED
  LIMIT :batch_size
)
UPDATE tasking.processing_tasks t
SET status = 'RUNNING',
    lease_owner = :worker_id,
    lease_expires_at = now() + :lease_interval,
    heartbeat_at = now(),
    attempt_count = attempt_count + 1,
    updated_at = now()
FROM picked
WHERE t.id = picked.id
RETURNING t.*;
COMMIT;
```

随后为每个任务插入 task_attempt。任务执行期间不持有领取事务。

### 9.4 租约心跳与完成

心跳条件更新必须包含 `id + status=RUNNING + lease_owner`。完成任务同样校验租约所有者；租约已失效的旧 Worker 不得提交成功覆盖新 attempt。

### 9.5 文档下线

锁定来源并校验 owner。更新为 OFFLINE、清空 pending version、递增 row_version，并创建取消未开始任务和索引下线任务。正在执行的任务通过后续状态校验停止，不能在持锁事务内等待 Worker。

### 9.6 保存问题并创建回答

同一短事务中：

1. 锁定 conversation；
2. 校验 ACTIVE 且不存在未终结回答；
3. 计算下一个 sequence_no；
4. 插入 user_message；
5. 插入 PENDING answer；
6. 更新 conversation.last_message_at；
7. 提交。

检索和模型调用在事务外执行。

### 9.7 回答完成与中止竞争

完成使用条件更新：

```sql
UPDATE conversation.answers
SET status='SUCCEEDED', content=:content, completed_at=now()
WHERE id=:answer_id
  AND status IN ('PENDING','RETRIEVING','STREAMING');
```

中止采用相同条件集合更新为 CANCELED。影响行数为 0 时重新读取终态并返回幂等结果。答案与 citations 在一个完成事务中写入；引用插入失败则答案不能提交为 SUCCEEDED。

## 10. 索引汇总

除主键和唯一约束外，首轮必须包含：

- `knowledge_sources(owner_user_id, status, updated_at DESC)`；
- `knowledge_sources(status, update_status)`；
- `document_versions(source_id, status, version_no DESC)`；
- `document_metadata(product_id, product_version_id, document_type_id)`；
- `document_chunks(version_id, ordinal)`；
- 任务领取部分索引和开放任务幂等部分唯一索引；
- `task_attempts(task_id, attempt_no DESC)`；
- `conversations(owner_user_id, status, last_message_at DESC)`；
- `user_messages(conversation_id, sequence_no)`；
- `answers(status, created_at)`，用于恢复扫描；
- `answer_citations(answer_id, citation_no)`；
- `answer_feedback(rating, updated_at)`，用于运营统计。

上线前使用真实查询和 `EXPLAIN (ANALYZE, BUFFERS)` 验证，不能仅凭字段“看起来会查询”就添加大量索引。

## 11. 数据保留与对象存储关系

- 用户、来源、版本、会话、消息、回答、引用、反馈和配置默认永久保留；
- 文档下线不删除原始对象、解析产物或成功版本；
- 会话逻辑删除不删除相关回答和引用；
- 导出文件可以按 `expires_at` 清理，但 export_artifact 记录保留；
- 对象存储删除必须由持久化清理任务执行，并在数据库记录结果；
- 搜索索引可重建，不在 PostgreSQL 保存向量副本；
- 数据库备份必须与对象存储版本备份形成可对应的恢复点。

## 12. 迁移与初始化

- Alembic 迁移文件进入代码仓库，禁止应用启动时自动修改生产表结构；
- 每个迁移包含 upgrade，关键迁移需提供可行的 downgrade 或明确不可逆及恢复方式；
- 初始化产品、文档类型、分类和系统配置使用版本化 seed，不在应用代码中静默创建；
- 大表加非空字段采用“先可空—回填—校验—设非空”的兼容步骤；
- 新旧应用并行发布时，迁移至少兼容前一个应用版本，破坏性删除延后一个发布周期。

## 13. 数据库测试要求

必须使用真实 PostgreSQL 容器验证：

1. 飞书 token 和 MD5 并发提交只有一个来源成功；
2. 下线来源后允许新来源使用相同 canonical_key；
3. 新版本失败时 current_version_id 不变；
4. 下线与版本激活并发最终为 OFFLINE；
5. 多 Worker 使用 SKIP LOCKED 不重复领取；
6. 租约失效的旧 Worker 不能提交完成；
7. 同一会话不能同时存在两个未终结回答；
8. 完成与中止并发只有一个终态；
9. 回答成功和 citations 保持原子性；
10. 分享快照不随原会话变化；
11. Alembic 从空库升级成功；
12. 备份恢复后业务主键与对象键关系完整。

## 14. 待确认事项

1. PostgreSQL 由项目自建还是使用公司托管实例；
2. DBA 是否允许创建多个 Schema、部分索引和必要扩展；
3. 用户账号停用后，其知识来源继续参与查询的建议是否确认；
4. 飞书原文删除后的自动策略：继续使用快照并告警，或自动下线；
5. 分享快照是否支持撤销；
6. 会话导出的首个文件格式；
7. 是否需要保存用户登录 IP；当前因取消审计需求而不保存，仅保留安全所需最小会话信息；
8. 配置修改是否需要双人确认；V1 当前按管理员直接激活设计。
