## 3. 与产品知识智能平台的主要差距

现有工程目前没有证据表明已经实现以下 V1 能力：

- 统一用户、密码登录、飞书身份匹配和系统会话；
- 知识来源、来源版本、解析产物、分类结果和索引发布状态；
- Word/PDF/Excel 本地文件上传、MD5/SHA-256 去重和所有权规则；
- 分类 Agent 读取数据库分类配置、低置信度待确认和不入库规则；
- `Fetch → Parse → Classify → Chunk → Embed → Index → Verify → Finalize` 流程；
- BM25 + 向量混合检索、RRF、Rerank、证据充分度判断和引用快照；
- 多轮知识问答、SSE 回答流、回答中止和引用失效提示；
- 会话归档、回收站、分享快照和 Markdown 导出；
- 来源优先级、LLM/Embedding/Rerank 运行配置版本；
- 知识库处理状态、系统运行统计和 V1 评测接口。

## 4. 现有路由与新平台路由的关系

现有主要路由前缀包括：

- `/cases`
- `/feishu/oauth`
- `/feishu/accounts`
- `/feishu/documents`
- `/admin/feishu`
- `/ai`
- `/ai/code`

它们属于现有案件管理、飞书同步和报告/代码 Agent 领域。新平台建议使用独立的 `/api/v1` 版本前缀，避免直接改变旧接口语义。

## 5. 推荐工程策略

### 5.1 不直接在旧领域模型上堆功能

旧工程中的 `Case`、`FeishuDocument`、`FeishuDocumentIndex` 和报告模型有既有业务含义。新平台应建立独立的知识库领域表和应用服务，通过来源 token、外部账号等必要字段与飞书能力对接。

### 5.2 先复用基础设施，再复用业务代码

优先复用：

1. FastAPI 启动和异常处理框架；
2. SQLAlchemy/Alembic 配置方式；
3. 飞书 OAuth 和文档 API 客户端经验；
4. 现有测试和配置管理方式。

不要直接复用：

1. 案件表作为知识文档表；
2. 旧的文档索引表作为 RAG 向量索引权威数据；
3. 现有定时任务代替 V1 数据库任务表；
4. 报告 Agent 接口代替知识问答 API。

### 5.3 API 文档生成策略

正式开发时以代码为准：

1. FastAPI Router 定义路径和状态码；
2. Pydantic v2 定义请求、响应和错误 Schema；
3. FastAPI 自动生成 OpenAPI JSON；
4. 从 OpenAPI JSON 导出或渲染 API 文档；
5. pytest/契约测试验证文档和实现一致。

当前 `outputs\详细设计\08_后端API与SSE接口_V0.1.md` 只作为实现前的接口设计基线，不应视为已经实现的 API 文档。

## 6. 当前结论与下一步

当前结论：

- 既有工程具备可复用的 FastAPI 和飞书接入基础；
- 不能直接宣称新平台 API 已实现；
- 新平台需要在确认代码落点后建立独立的 V1 模块和数据库迁移；
- API 文档应在第一批 Router、Schema 和测试完成后由 FastAPI OpenAPI 生成。
