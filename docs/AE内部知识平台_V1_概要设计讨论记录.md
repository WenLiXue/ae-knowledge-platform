## 2. 概要设计目标

概要设计回答“系统整体怎么做”，主要需要明确：

1. 系统由哪些业务模块和技术模块组成；
2. 每个模块负责什么、不负责什么；
3. 模块之间如何协作和传递数据；
4. 核心业务对象及其状态如何管理；
5. 外部系统和模型服务如何接入；
6. 系统如何部署、存储、异步处理、失败恢复和扩展；
7. 如何满足 V1 的可靠性、可维护性和可测试性要求。

当前阶段先确认模块职责和业务边界，不急于画图或选择具体技术产品。

## 3. 已确认的总体原则

### 3.1 业务与技术分层

- 知识来源管理、知识治理、知识查询等属于业务模块。
- RAG、BM25、向量检索、Rerank 和大模型属于模块内部使用的技术能力。
- 数据库、对象存储、检索引擎和任务队列属于基础设施，不与业务模块处于同一层级。
- 问题诊断是未来独立业务模块；CDT 日志分析是问题诊断模块下的具体业务用例。

### 3.2 V1 范围

- V1 优先完成产品知识查询闭环。
- V1 不建设问题诊断和 CDT 日志分析功能，但整体设计应避免阻碍后续扩展。
- 已取消权限和审计相关产品需求，概要设计不继续展开对应模块和流程。

### 3.3 部署与服务调用

- 系统使用一套部署架构，不区分两套“内网架构”和“公网架构”。
- 公网环境可使用域名、HTTPS 和反向代理访问。
- 内网环境可通过内网域名或地址访问。
- 业务模块、数据模型和处理流程保持一致，差异通过环境配置解决。
- 飞书、大模型、Embedding 和 Rerank 等能力统一通过 HTTP 接口调用；本地服务和外部服务不做业务架构上的区别。

### 3.4 初步实现形态

- V1 预计约 30 名用户，不采用微服务拆分。
- 采用模块化单体应用组织业务代码和接口。
- 文档获取、解析、分类、切片、索引、每日同步和失败重试等耗时任务由独立异步任务执行单元处理。

## 4. 业务模块划分修正

状态：讨论中。

原方案将“用户与飞书连接、知识来源管理、知识治理、知识查询、对话与反馈、系统运营管理”并列为六个业务模块。该划分存在以下问题：

- “用户与飞书连接”是一项具体功能，不是独立业务领域；
- “知识来源管理”和“知识治理”更适合作为知识库管理内部的职责；
- “知识查询”和“对话与反馈”共同构成用户完整的智能问答过程；
- 原方案混合了一级业务模块、二级功能和系统支撑能力，粒度不一致。

当前建议将 V1 一级业务模块收敛为以下三个：

1. **知识库管理**：负责知识接入、重复识别、文档所有权、解析、分类、索引、同步、更新和下线；
2. **智能问答**：负责自然语言提问、查询条件、知识检索、答案生成、来源引用、多轮会话和用户反馈；
3. **系统管理**：负责用户管理、文档处理情况、异常任务、人工重试、待确认内容、运行统计和系统配置。

以下内容作为支撑能力或内部职责，不单独作为一级业务模块：

- 登录和飞书账号绑定：作为用户基础能力，并服务于知识接入；
- 知识接入、知识治理：作为知识库管理内部子模块；
- 对话管理、用户反馈：作为智能问答内部子模块；
- 异步任务、模型调用、检索引擎和数据存储：作为技术支撑模块。

未来的问题诊断可作为独立一级业务模块扩展，CDT 日志分析属于问题诊断下的具体用例。

### 4.1 系统管理中的用户管理

用户管理不应遗漏，但不建议单独拆成与知识库管理、智能问答并列的一级业务领域。当前建议作为系统管理下的子模块，至少负责：

- 用户账号信息；
- 用户账号状态；
- 飞书账号绑定状态；
- 重新绑定或解除绑定；
- 用户最后登录时间等基础信息。

由于 V1 已取消权限体系，用户管理暂不包含复杂的角色授权、文档权限和数据权限配置。

### 4.2 登录方式

已确认系统同时保留两种登录入口：

1. 系统账号和密码登录；
2. 飞书扫码登录。

两种登录方式最终都进入同一套系统用户体系。

飞书扫码登录规则确认为：

- 系统取得 UserInfo 中的飞书 `user_id`；
- 已存在对应的飞书身份记录时，直接登录关联的系统用户；
- 不存在对应记录时，自动创建系统用户和飞书身份记录，完成注册并登录；
- 创建系统用户和绑定飞书身份必须在同一事务中完成；
- `tenant_key + feishu_user_id` 必须建立唯一约束，避免并发扫码产生重复账号；
- 扫码注册后的用户可以设置系统用户名和密码，以后也可以使用账号密码登录；
- 不开放独立的账号密码自主注册，避免形成无法自动关联的重复用户；
- 管理员可以为无飞书账号、测试或其他例外场景创建系统账号；
- 已绑定飞书的用户可以通过飞书扫码验证后重置密码，未绑定飞书的例外账号由管理员重置密码；
- 用户解除飞书绑定后，仍可使用已经设置的系统账号和密码登录，但不能继续发现或提交自己的飞书文档；
- 飞书授权失效不删除系统账号、历史会话和已经提交的知识记录；
- 系统账号被停用时，账号密码和飞书扫码两种登录方式均不可使用。

### 4.3 飞书身份唯一键

飞书授权登录取得 UserInfo 后，使用其中的飞书 `user_id` 识别飞书用户。为了避免与系统内部用户编号混淆，数据库字段命名为 `feishu_user_id`。

建议的数据关系为：

- 系统用户表使用系统生成的内部 `id` 作为主键；
- 飞书身份表保存 `tenant_key`、`feishu_user_id`、`open_id`、`union_id` 和关联的内部用户 `id`；
- 使用 `tenant_key + feishu_user_id` 建立唯一约束；
- `open_id` 和 `union_id` 作为辅助标识保留，便于调用其他飞书接口和后续排查；
- `user_access_token` 和临时授权码都有时效性，只用于授权调用，不能作为用户唯一键。

获取 UserInfo 中的飞书 `user_id` 需要相应的用户 ID 字段权限，具体实现阶段应配置最小必要权限。

官方字段依据：[飞书开放平台·获取用户信息](https://open.feishu.cn/document/server-docs/authentication-management/login-state-management/get.md)。

## 5. 知识库管理：知识接入子模块

状态：基本确认。

### 5.1 模块边界

知识接入子模块负责用户发现、选择并提交知识来源。提交成功后，由知识治理子模块接管后续处理。

该模块不负责：

- 判断文档是否与产品相关；
- 自动分类和提取业务字段；
- 文档切片和索引；
- 根据文档生成问答答案。

### 5.2 知识来源接入方式

支持以下方式：

1. 用户绑定飞书后，查看自己可见的飞书文档元数据并多选提交；
2. 用户直接粘贴飞书文档链接提交；
3. 用户上传 Word、PDF、Excel 等本地文件。

发现飞书文档时只读取标题、类型、所属位置、修改时间等元数据。只有用户明确选择并提交后，系统才获取正文并进入知识治理流程。

### 5.3 重复识别

- 飞书文档使用底层文档唯一 token 判断是否重复，不能仅根据 URL 判断。
- Word、PDF、Excel 等本地文件根据文件内容计算 MD5，使用 MD5 判断完全相同的文件。
- 文件名或上传路径不同，但 MD5 相同，仍视为重复文件。
- 文件内容改变后 MD5 改变，系统不能仅凭新文件自动判断它是旧文档的新版本。
- 用户在已有文档上执行“更新文档”时，即使新文件 MD5 改变，也作为原知识来源的新版本处理。
- 用户执行“上传新文档”时，新的 MD5 视为新的知识来源。

### 5.4 所有权与重复提交

- 首次成功提交文档的用户成为该知识来源的所有者。
- A 首次提交后，B 再次提交相同文档，系统提示文档已经存在。
- 重复提交不重复解析、分类和建立索引。
- B 不获得该文档的更新、撤回、删除或下线权利。
- B 仍可正常查询已经入库的知识。

### 5.5 撤回与重新提交

- 文档成功入库后，所有者可以自行撤回或下线。
- 文档下线后不再参与新查询。
- 系统保留文档业务记录；历史对话中的引用信息继续保留。
- 用户访问已失效的原文时，提示来源已下线、已删除或不可访问。
- 原所有者下线文档后，其他用户可以重新提交相同文档，并成为新的所有者。

## 6. 知识库管理：知识治理子模块

状态：讨论中。

### 6.1 模块目标

负责将用户提交的原始文档处理为可供知识查询使用的内容。

### 6.2 已讨论职责

1. 获取飞书正文、附件或本地上传文件；
2. 解析正文、标题、章节、表格和必要的附件信息；
3. 判断文档与当前产品知识库的相关性；
4. 由知识治理 Agent 自动分类并提取业务字段；
5. 进行章节识别、表格保留、文档切片和上下文补充；
6. 建立关键词索引和向量索引；
7. 每日检查已提交飞书文档的修改时间或 revision，并在发生变化时触发更新；
8. 记录失败阶段和失败原因，最多自动重试三次，之后允许人工重新执行。

### 6.3 已确认的入库规则

- 内容相关且分类字段完整：正常入库。
- 内容相关但部分分类字段无法判断：允许入库，未知字段留空，并记录待完善字段。
- 治理 Agent 不得为了完成分类而编造产品、版本或其他业务字段。
- 是否相关无法判断：进入“待确认”，不参与查询。
- 明确无关：标记为“不予入库”，不参与查询。
- 文档解析、分类、切片和索引全部成功后，才进入“入库成功”状态。

### 6.4 文档更新失败与版本切换

已确认采用以下规则：

- 已入库的飞书文档出现新版后，系统创建新版处理任务；
- 新版获取、解析、分类或建立索引失败时，保留旧的成功版本继续参与查询；
- 后台将文档标记为“新版同步失败”，记录失败阶段和原因；
- 自动重试最多三次，三次失败后进入异常任务，由管理员手动重试；
- 新版全部处理成功后，再将查询版本一次性切换到新版；
- 新版切换成功后清理旧版索引；
- 系统不向普通用户提供历史版本选择，正常查询使用最新成功版本。

## 7. 智能问答模块

状态：讨论中。

### 7.1 模块职责

智能问答模块面向用户完成从自然语言提问到获得有依据答案的完整过程，初步包含：

1. 会话管理：新建会话、保存会话、查看历史会话以及多轮追问；
2. 问题理解：结合当前问题、会话上下文和查询条件理解用户意图；
3. 知识检索：根据问题自动检索相关知识，不要求用户预先选择问题类型或文档来源；
4. 答案生成：基于检索依据组织答案，并展示来源链接；
5. 来源与反馈：展示答案依据，收集“有帮助 / 没有帮助”反馈及可选原因。

### 7.2 查询条件作用范围

- 产品、版本和文档类型等属于可选查询条件，不是用户提问前必须填写的内容；
- 查询条件用于缩小知识范围，系统仍根据自然语言问题自动选择和检索相关文档；
- 查询条件属于会话级状态，在同一会话的多轮追问中持续生效；
- 用户可以在当前会话中修改或清空查询条件；
- 新建会话时不继承上一会话的查询条件，恢复为未筛选状态；

### 7.3 自然语言条件与会话条件的优先级

- 用户在当前问题中明确表达的新产品、版本或文档类型，优先于同一维度的原会话条件；
- 系统使用新条件替换对应维度的会话条件，并将其用于后续追问；
- 当前问题没有涉及的其他会话条件继续保留；
- 条件发生变化时，界面应明确展示变更结果，避免用户不知道实际查询范围已经变化；
- 如果用户使用“新版本”“另一个产品”等无法唯一确定的表达，系统不得自行猜测，应先要求用户补充具体条件；
- 用户也可以主动清空某一项或全部会话查询条件。
